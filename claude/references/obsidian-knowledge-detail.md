# ナレッジ管理 — 詳細ガイド

## メモを書くタイミング一覧

以下は代表的なタイミングである。
表にない場面でも、再利用価値のある情報は書く。

| タイミング | 記録内容 | 例 |
|---|---|---|
| **設計判断時** | 選択肢・採用理由・却下理由 | 「状態管理にPiniaを採用。Vuexは非推奨のため却下」 |
| **ハマりポイント解決時** | 問題・原因・解決策 | 「Nuxt useFetchはSSR時にcookieを自動転送しない→useRequestHeadersで明示的に渡す」 |
| **ユーザーの好み・方針を聞いた時** | 好み・方針の内容 | 「エラーハンドリングはResult型パターンを好む」 |
| **環境・インフラの知見** | 設定値・手順・注意点 | 「本番DBはCloud SQL、接続にはCloud SQL Proxyが必要」 |
| **外部API・ライブラリの癖** | 挙動・制約・ワークアラウンド | 「Stripe WebhookはContent-Type: application/jsonでないと署名検証が失敗する」 |
| **タスク完了時** | 実装概要・変更点・残課題 | 「認証フローをJWT→セッションに変更。リフレッシュトークンは未実装」 |
| **調査で分かったこと** | コードの仕組み・依存関係・制約 | 「認証ミドルウェアはserver/middleware/auth.tsで一括処理」 |
| **試行錯誤の過程** | 試したこと・失敗した理由 | 「pnpm v9ではpeer depsの自動インストールがデフォルトOFF」 |
| **ユーザーの暗黙的な好みを検知した時** | 修正・指摘から読み取れる好み・スタイル | 「変数名を修正された→略語より完全な単語を好む」 |
| **ビルド・テスト手順を発見した時** | 実行コマンド・前提条件・注意点 | 「E2Eテストは `docker compose up -d` でDB起動後に実行する必要がある」 |
| **タスクを中断・引き継ぐ時** | 現在の状態・次にやること・ブロッカー | 「認証機能の実装中。トークンリフレッシュが未完了、APIスキーマ確定待ち」 |

## タスク完了前のセルフチェック

タスク完了を報告する前に、以下を自問すること。1つでも該当すればメモを書く:

- 次に同じタスクをやる人が知っておくべきことはあるか?
- 調査中に「これは知らなかった」と思ったことはあるか?
- ユーザーが口頭で伝えた方針・好みはあるか?
- エラーや想定外の挙動に遭遇したか?
- 既存コードの設計意図を理解するのに時間がかかった箇所はあるか?
- ユーザーの修正・指摘から暗黙的な好みを読み取れたか?
- ビルドやテストの実行手順で試行錯誤したか?
- このタスクは未完了で、次回セッションに引き継ぐ必要があるか?

## フロントマター規約（必須）

すべてのノートの先頭に YAML フロントマターを付けること。
このVaultの入口は `obsidian search` である。
本文の構造よりも「検索で正しいノートに当たること」「冒頭だけで要旨が掴めること」を優先する。

```yaml
---
type: troubleshooting
status: active
project: axelzero-purchase
date: 2026-08-18
summary: 3DS失敗後の再試行で決済成功してもセッションが failure のまま残る
tags: [payment, 3dsecure, incident]
---
```

| フィールド | 必須 | 内容 |
|---|---|---|
| `type` | ✓ | ノート種別。`design-decision` / `troubleshooting` / `runbook` / `til` / `handover` のいずれか |
| `status` | ✓ | 鮮度。下表参照 |
| `project` | ✓ | 配置ディレクトリ名と同じ。ディレクトリ名は rules/obsidian-knowledge.md の「プロジェクト名の判定」（リポジトリ名基準）に従う |
| `date` | ✓ | 作成日（YYYY-MM-DD） |
| `summary` | ✓ | 結論を1行で。検索結果からノートを判別するために使う |
| `tags` | 任意 | トピックタグ（例: `payment`, `k6`, `incident`）。後述のタグ規約を参照 |

### status の値

| 値 | 意味 |
|---|---|
| `active` | 現在有効な知見 |
| `investigating` | 未解決・調査中（troubleshooting / handover 向け） |
| `outdated` | 古くなった。参照時は裏取りすること |
| `superseded` | 別ノートで置き換え済み。本文冒頭に後継ノートへのリンクを置く |

古い知見をAIがそのまま信じる事故を防ぐため、無効になったと気づいたノートは放置せず `status` を `outdated` / `superseded` に更新すること。

## ノート種別テンプレート

種別ごとに以下のセクション構成を基本とする。
内容に応じてセクションを追加してよい。
既定セクションは省略せず、該当がない場合は `- なし` と明記する（課題作成テンプレートと同じ運用）。

### design-decision（設計判断 = ADR形式）

| セクション | 内容 |
|---|---|
| 背景 | 背景・課題・制約 |
| 決定 | 採用した選択肢と理由 |
| 却下した選択肢 | 検討したが採らなかった選択肢と却下理由 |
| 影響 | 影響・トレードオフ・残課題 |

### troubleshooting（ハマりポイント・外部APIの癖・インシデント）

| セクション | 内容 |
|---|---|
| 症状 | エラーメッセージ・事象を**原文のまま**書く。次に踏んだ人はこの文字列で検索する |
| 原因 | 根本原因。ファイルパス・行番号など具体的に |
| 解決策 | 実際に効いた対処。コマンド・コードはコピペ可能な形で |
| 再発防止・注意点 | ガード方法・追加すべきテスト・類似の危険箇所 |

### runbook（環境・インフラ・ビルド/テスト手順）

| セクション | 内容 |
|---|---|
| 前提 | 必要な権限・ツール・環境変数 |
| 手順 | コピペ可能なコマンド列 |
| 検証 | 成功をどう確認するか |
| 注意点 | 落とし穴・やってはいけないこと |

### til（小さな知見・ユーザーの好み）

| セクション | 内容 |
|---|---|
| 結論 | 1〜3行 |
| 詳細 | 根拠・出典・きっかけになったやりとり |

### handover（タスク中断・引き継ぎ）

| セクション | 内容 |
|---|---|
| 現在の状態 | 完了した作業・ブランチ・コミット |
| 次にやること | 未着手の作業を具体的に |
| ブロッカー | 待ち状態・確認が必要なこと |

## 本文の書き方

- **結論を先頭に書く（逆ピラミッド）。**
  経緯・詳細・時系列は後半に置く。
- 追記は末尾に `## 追記: <題> (YYYY-MM-DD)` として積む。
  **追記で結論が変わったら、フロントマターの `summary` と冒頭の結論も必ず書き換えること。**
  「時系列ログは下部、現在の正解は冒頭」で両立させる。
- エラーメッセージ・識別子・コマンドは原文（英語）のまま書く。
  日本語に翻訳すると検索でヒットしなくなる。

## タグ規約

`type` と `project` はフロントマターのフィールドで表現するため、タグはトピックの補足に使う。

- `#user-preference` — ユーザーの好み・方針（type: til と併用）
- `#api-quirk` — 外部API・ライブラリの癖（type: troubleshooting と併用）
- `#incident` — 本番影響のあった事象
- その他、`#payment` `#k6` などドメイン・技術のトピックタグは自由に付けてよい

コマンドの使い方は `/obsidian-cli` スキルを参照すること。
