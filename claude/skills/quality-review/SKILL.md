# Google Engineering Practices コードレビュー

PRの差分を Google Engineering Practices の原則に基づき、12の観点でレビューする。

> コードレビューの目的は「コードベースの全体的な品質を継続的に改善すること」である。CLが全体的にコード品質を改善しているなら、完璧でなくても承認すべきだ。完璧なコードは存在しない — より良いコードがあるだけだ。

## 使い方

```
# 現在のブランチの差分をレビュー（未ステージ + ステージ済み）
/quality-review

# 直近コミットをレビュー
/quality-review HEAD~1

# PR全体をレビュー（ベースブランチとの差分）
/quality-review --pr

# 努力レベルを指定（low: 高確度の問題のみ / high: 広範なカバレッジ。他の引数と組み合わせ可能）
/quality-review --effort high
/quality-review --pr --effort high

# GitHubにコメントを投稿（下書き）
/quality-review --comment
```

## 基本原則

レビューコメントを書く際、以下の原則に従う。これらは Google Engineering Practices が長年の実践から導いたものであり、レビューの質と開発者との信頼関係を左右する。

### 技術的事実で判断する

個人の好みではなく、技術的根拠に基づいて指摘する。「私はこう書く」ではなく「このパターンは〜の問題を引き起こす」のように客観的な理由を示す。スタイルガイドが存在する場合、スタイルに関する議論はガイドに従って終わりにする。

### コードに対してコメントし、人を批判しない

- NG: 「あなたはなぜここで〜したのですか」
- OK: 「このコードは〜の理由で〜に変更すると改善できます」

### 理由を必ず説明する

指摘には「なぜそうすべきか」を添える。理由のない指摘は説得力がなく、開発者が優先順位を判断できない。

### コードの改善を促す

レビューツール内での説明を求めるのではなく、コード自体をより明確に書き直すよう促す。説明がないと理解できないコードは、将来の読者も同じように困惑する。

## 実行手順

### Step 1: レビュー対象の特定

引数に応じて diff を取得する:

- **引数なし**: `git diff` + `git diff --staged` で未コミットの変更を対象にする
- **`HEAD~N`**: `git diff HEAD~N` で直近Nコミットの差分を対象にする
- **`--pr`**: `gh pr view --json number,baseRefName` で現在のブランチのPRを特定し、`git diff <baseRefName>...HEAD` で差分を取得する。PRが見つからない場合はその旨を伝えて中断する

差分が空の場合は「レビュー対象なし」と明示して終了する。

### Step 2: 文脈の把握

差分だけでは変更の意図や影響を正確に判断できない。以下の周辺コードを文脈として読み取る:

- 変更されたファイルの全体構造
- 変更箇所の呼び出し元・呼び出し先
- 関連する型定義・インターフェース
- 関連するテストファイル
- 変更に関わるルーティング定義やミドルウェア

ただし、**指摘は差分行に対してのみ**行う。差分外のコードへの指摘はノイズになる。

### Step 3: CLの全体像を評価する

個々のコード行を見る前に、変更の全体像を把握する:

- この変更は妥当か？（そもそもこのアプローチで正しいか）
- 設計上の大きな問題はないか？

大きな設計上の問題がある場合は、細かい指摘に入る前に早期にフィードバックする。開発者が枝葉の修正に時間を費やした後に根本的な方向転換を求めるのは非効率的だ。

### Step 4: 12の観点でレビュー

`references/review-perspectives.md` を読み込み、以下の12観点で差分を検証する。

#### Google 8 観点

1. **設計（Design）** — システムに適切に設計されているか、コンポーネント間の相互作用が理にかなっているか
2. **機能性（Functionality）** — 意図通りに動作するか、ユーザーにとって有益か、エッジケース・並列処理の安全性
3. **複雑性（Complexity）** — 不必要に複雑でないか、過剰な汎用化（YAGNI違反）がないか、将来の読者が理解・修正できるか
4. **テスト（Tests）** — テストが正確で十分か、テスト自体が保守しやすいか
5. **命名（Naming）** — 変数・クラス・メソッド名が意図を明確に表しているか
6. **コメント（Comments）** — 「Why」のみを説明しているか、「What」はコード自体で表現すべき
7. **スタイル（Style）** — スタイルガイドに従っているか、既存コードとの一貫性
8. **ドキュメント（Documentation）** — 関連ドキュメントが更新されているか

#### 追加 4 観点

9. **セキュリティ（Security）** — ハードコードシークレット、入力検証、SQLi、XSS、CSRF、認証・認可、エラーメッセージの情報漏洩
10. **パフォーマンス（Performance）** — N+1クエリ、不要な SELECT *、インデックス、バルク処理、キャッシュ、Promise.all 漏れ、ストリーム処理、タイムアウト
11. **型安全性（Type Safety）** — any/unknown キャスト、null/undefined 処理、例外境界、スキーマ検証、Promise 握りつぶし
12. **負荷耐性（Load Resilience）** — レート制限、サーキットブレーカー、バックプレッシャー、コネクションプール枯渇、リトライストーム、サンダリングハード

各観点の詳細なチェック項目は `references/review-perspectives.md` を参照する。

#### Google Cloud 利用時の追加チェック（負荷耐性の深掘り）

差分に Google Cloud サービスの利用が含まれる場合、`references/gcp-rate-limits.md` を**必ず**読み込み、観点12の検証に用いる。
GCP利用と判定する具体的なシグナル（import・エンドポイント・クライアント・インフラ定義）は、同ファイルの「差分にGCP利用が含まれるかの判定シグナル」の定義に従う。

Google Cloud のクォータはプロジェクト単位・分単位のものが多く、開発環境では顕在化せず本番の高負荷時に初めて障害となる。
静的なコード構造（ループ内API呼び出し・無制限並列・リトライ設計）から事前に検出できるのはレビューだけであるため、このチェックは省略しない。

#### `--effort` によるレビュー深度の調整

| 指定 | 検証範囲 | 報告する指摘 |
|---|---|---|
| `low` | 12観点を概観し、高確度の問題に絞って検証する | must と重大な imo のみ。nit / fyi / q は報告しない |
| 指定なし | 12観点を通常の深度で検証する | 全ラベル |
| `high` | `references/review-perspectives.md` の全チェック項目を網羅的に照合する | 全ラベル。nit レベルの軽微な改善も拾う |

### Step 5: 指摘の作成

各指摘に以下の5種のラベルのいずれかを付与する。
表は重要度の高い順（= 後述する採番順）に並べている。

| ラベル | 意味 | 対応方針 | 文末トーン |
|---|---|---|---|
| **must** | 修正必須。バグ・セキュリティ・実害あるパフォーマンス問題 | マージ前に必ず修正 | 「〜を〜のように修正してほしいです。」 |
| **imo** | 改善提案。設計・可読性・個人の意見 | 検討推奨。対応は任意 | 「〜を〜のように修正したほうがいいと思います。」 |
| **nit** | 軽微な指摘。スタイル・命名の些細な改善 | 対応は任意。ブロッカーではない | 提案調 |
| **q** | 質問・確認 | 回答が必要 | 「〜ですか？」 |
| **fyi** | 参考情報・補足 | 読むだけでよい | 説明調 |

ラベルの判定基準:

- セキュリティ問題（シークレット漏洩、SQLi、認可バイパス等）→ **例外なく must**
- N+1・キャッシュ欠落で実害が見込まれる → **must**
- 設計・可読性の改善提案 → **imo**
- スタイル・命名の些細な改善 → **nit**
- 意図が読み取れず判断できない → **q**
- 迷ったら弱い方に倒す（must か imo で迷ったら imo）

#### 指摘への連番付与

各指摘に**1から始まる連番**を振る。ユーザーが「3番について詳しく」のように番号で指摘を指定できるようにするためである。

番号は以下の順序で割り当てる。番号と指摘の対応を一意に定めるため、この順序から外れてはならない。

1. ラベルの重要度順に並べる: **must → imo → nit → q → fyi**
2. 同一ラベル内はファイルパスの昇順、次に行番号の昇順で並べる

### Step 6: 承認判断

全指摘を出し終えたら、変更全体を以下の基準で判断する:

- **LGTM（承認推奨）**: must が 0 件で、変更が全体的にコード品質を改善している
- **LGTM with nits**: must が 0 件で nit のみ。承認してよいが軽微な改善を提案
- **要修正**: must が 1 件以上。修正後に再レビューが必要
- **要相談**: 設計レベルの根本的な問題がある。方向性の議論が必要

## 出力フォーマット

### チャット出力

```markdown
## サマリ

**判定: LGTM with nits**
must 0 / imo 1 / nit 2 / q 1 / fyi 0
設計は適切で、全体的にコード品質を改善している。命名に関する軽微な指摘が2件。

## 指摘

1. [imo] `server/utils/oidc.ts:30-35`
   このtry-catchブロック内のエラーハンドリングを、関数の呼び出し元に委ねたほうがいいと思います。
   現在の実装ではエラーを握りつぶしており、デバッグ時に問題の特定が困難になるためです。

2. [nit] `server/utils/oidc.ts:42`
   `res` は `tokenResponse` のように具体的な名前にすると、呼び出し側で何のレスポンスか明確になります。

3. [nit] `server/utils/oidc.ts:58`
   `data` は `userProfile` の方が内容を表す名前です。

4. [q] `server/utils/oidc.ts:15`
   この定数 `MAX_RETRY` が 5 に設定されていますが、この値の根拠はありますか？

## レビュー範囲

git diff main...HEAD（3ファイル、+120/-45行、abc1234...def5678）
```

### 詳細説明を求められた場合

ユーザーは「3番」「指摘 3」のように連番で対象を指定できる。
特定の指摘について詳細を求められたときのみ、以下を展開する:

- 問題のメカニズム（なぜ起きるか・どんな実害があるか）
- 修正提案を **before / after** 形式で提示
- 修正困難な場合は選択肢を提示

最初の出力に先回りして詳細を載せないこと。

### GitHub 投稿（`--comment` 指定時またはユーザーから求められた場合のみ）

PRにインライン下書きコメントとして投稿する。submit せず、ユーザーが内容を確認してから提出する。

バッジ画像をコメントの1行目に置く:

| ラベル | バッジ |
|---|---|
| must | `![must-badge](https://img.shields.io/badge/review-must-red)` |
| imo | `![imo-badge](https://img.shields.io/badge/review-imo-orange)` |
| nit | `![nit-badge](https://img.shields.io/badge/review-nit-yellow)` |
| q | `![q](https://img.shields.io/badge/review-q-success.svg)` |
| fyi | `![fyi](https://img.shields.io/badge/review-fyi-orange.svg)` |

バッジの次の行から指摘本文を書く。
連番はチャット出力内での参照用であり、GitHub コメント本文には含めない。

投稿手順:

1. `GET /repos/{owner}/{repo}/pulls/{number}/files` で diff の position を取得する
2. `POST /repos/{owner}/{repo}/pulls/{number}/reviews` で `event` を省略（PENDING）し、`comments[]` にインラインコメントを含める
3. ローカルの行番号と diff の position がズレる場合があるため、`patch` フィールドで位置を検証する

## セキュリティ重大問題検出時

シークレット漏洩・SQLi・認可バイパスなど、セキュリティ事故・データ破壊・本番障害に直結する問題を検出した場合:

1. **作業を停止する**
2. 該当箇所と影響範囲をユーザーに**即座に報告**する
3. 漏洩シークレットがあれば**ローテーション手順を案内**する
4. ユーザーの判断を仰いだうえで修正に着手する

黙ってスキップしたり、独断で修正してマージへ進めないこと。

## やらないこと

- 差分外のコードへの指摘（文脈として読むが、指摘は差分行のみ）
- コードの自動修正（指摘のみ。修正は開発者の責務）
- 個人の好みに基づく指摘（技術的根拠のない「私ならこう書く」は避ける）
- 完璧さの追求（コード品質が改善されていれば承認する）
