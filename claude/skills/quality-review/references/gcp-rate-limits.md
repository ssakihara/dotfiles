# Google Cloud レートリミット・クォータ 詳細チェックリスト

SKILL.md の Step 4 で、差分に Google Cloud サービスの利用が含まれる場合に読み込む。
観点12（負荷耐性）の検証をGoogle Cloud固有のクォータ知識で深掘りするためのファイルである。

## なぜレビューで検出する必要があるか

Google Cloud のクォータの多くは**プロジェクト単位・分単位**で計測される。このため:

- 開発環境や単体テストでは絶対に顕在化しない（負荷が桁違いに小さい）
- 本番の高負荷時に初めて 429 / `RESOURCE_EXHAUSTED` が発生し、障害として顕在化する
- 1インスタンスでは問題なくても、オートスケールで N 台に増えると合算負荷がクォータを超える

つまり「動くコード」がレビューをすり抜けると、**次に問題が見つかるのは本番障害のとき**になる。
コードの静的な構造（ループ内呼び出し・無制限並列・リトライ設計）からリスクを検出できるのはレビューだけである。

## 差分にGCP利用が含まれるかの判定シグナル

以下のいずれかが差分に含まれる場合、このファイルのチェックを適用する:

- import / require: `@google-cloud/*`, `firebase-admin`, `firebase-functions`, `googleapis`, `google-auth-library`
- RESTエンドポイント: `*.googleapis.com` へのHTTP呼び出し
- クライアント: `Firestore`, `Storage`, `PubSub`, `BigQuery`, `SecretManagerServiceClient`, `CloudTasksClient`, `Logging` 等のインスタンス化・メソッド呼び出し
- インフラ定義: Cloud Run / Cloud Functions / App Engine の設定ファイル（`app.yaml`, `service.yaml` 等）

## 検出パターン（コードの匂い）

差分から静的に検出できる代表的な危険パターン。**サービス別の数値を暗記するより、まずこの構造パターンで検出する。**

### P1: リクエストパス・ループ内での管理系API呼び出し

Secret Manager・IAM・Resource Manager・IAM Credentials 等の管理系APIは、データ系APIに比べて**クォータが桁違いに低い**。
リクエストごと・ループごとに呼び出す実装は、トラフィック増加に比例してクォータを消費する。

- ❌ リクエストハンドラ内で毎回 `accessSecretVersion()` を呼ぶ → 起動時に取得しメモリにキャッシュする
- ❌ 署名付きURLの生成でリクエスト毎に IAM Credentials API（`signBlob`）を呼ぶ → 生成結果のキャッシュや有効期限の見直しで呼び出し頻度を下げる（サービスアカウントキーによるローカル署名は長期鍵の保管・漏洩リスクがあるため原則避け、差分に含まれる場合はセキュリティ観点で指摘する）
- ❌ ループ内で `getIamPolicy` / `testIamPermissions` を呼ぶ → 事前に一括取得する

### P2: 無制限の並列ファンアウト

`Promise.all(items.map(item => gcpCall(item)))` は items が増えるほど瞬間的なリクエストレートが跳ね上がる。
分単位のクォータは「平均」ではなく「バースト」で超過する。

- ❌ 件数上限のない配列に対する `Promise.all` での一斉GCP呼び出し
- ✅ `p-limit` 等で同時実行数を制御する、またはバッチAPIに置き換える
- 判定基準: items の件数に上限があるか（固定長ならOK、ユーザー入力・DB件数依存なら危険）

### P3: 同一リソースへの高頻度書き込み（ホットスポット）

- Firestore: 同一ドキュメントへの持続的な書き込みは **1回/秒** が目安。カウンタ・集計値の直接更新は危険 → 分散カウンタ（シャーディング）を使う
- Firestore / Cloud Storage: 連番・タイムスタンプ先頭のドキュメントID・オブジェクト名はホットスポットを生む → ランダム性のあるIDにする
- Cloud Storage: 同一オブジェクト名への書き込みは **1回/秒** が目安

### P4: 429 / `RESOURCE_EXHAUSTED` を想定しないエラーハンドリング

クォータ超過は「異常」ではなく高負荷時に**必ず起こる正常系の一部**として設計する必要がある。

- ❌ catch して即時リトライ・固定間隔リトライ → リトライストームを起こし、クォータ回復を妨げる
- ❌ 429 を他のエラーと同一視して無限リトライ
- ✅ エクスポネンシャルバックオフ + ジッター。公式クライアントライブラリの組み込みリトライ設定を確認する
- ✅ リトライ回数上限と、上限到達時のフォールバック（DLQ・グレースフルデグラデーション）

### P5: バッチAPIを使わない逐次・行単位呼び出し

- ❌ ループ内で1件ずつ Firestore write → `BulkWriter` / `batch()`（1バッチ最大500操作）
- ❌ BigQuery へ1行ずつ `insert` → まとめて Storage Write API / ロードジョブ
- ❌ Pub/Sub へ1件ずつ publish → バッチパブリッシュ設定を使う
- ❌ ループ内で1エントリずつ Cloud Logging write → クライアントのバッファリングに任せる

### P6: クライアント・コネクションの都度生成

リクエストごとに `new Firestore()` 等でクライアントを生成すると、認証トークン取得（これ自体がクォータ対象）と
コネクション確立が毎回発生する。クライアントはモジュールスコープで生成し使い回す。

### P7: スケールアウトの合算を考慮しない設計

クォータは**プロジェクト単位**が基本。コード上は低頻度に見えても:

- Cloud Run / Functions がスパイクで100インスタンスに増えれば、起動時処理も100倍になる
- 各インスタンスの定期ポーリング（ヘルスチェック・設定リロード）はインスタンス数に比例する
- レビュー時は「この処理 × 最大インスタンス数」で見積もる

## サービス別クォータ早見表

代表値の目安（変更されうるため、mustを付ける前に規模感だけ確認する。正確な値は[公式ドキュメント](https://cloud.google.com/docs/quotas)参照）:

| サービス | 制限 | 目安 | レビューでの着眼点 |
|---|---|---|---|
| Firestore | 同一ドキュメント書き込み | 1回/秒（持続） | カウンタ・ステータス更新の集中 |
| Firestore | バッチ/トランザクション | 500操作 | 500件超のループバッチ |
| Cloud Storage | 同一オブジェクト書き込み | 1回/秒 | ログ追記・上書き更新パターン |
| Secret Manager | アクセス要求 | 分単位/プロジェクト | リクエストパスでの都度取得 |
| Cloud Tasks | キューのdispatch | 500回/秒/キュー（デフォルト） | 一斉投入時のレート設定 |
| BigQuery | テーブル変更（DML/ロード） | 1,500回/日/テーブル | 細切れのINSERT/UPDATEジョブ |
| BigQuery | 同時実行クエリ | 100（インタラクティブ） | リクエスト連動のクエリ発行 |
| Pub/Sub | パブリッシュスループット | リージョン単位クォータ | 大量メッセージの無制御送信 |
| Cloud Logging | 書き込みAPI | 分単位/プロジェクト | ループ内の同期ログ出力 |
| 管理系API（IAM, Compute, Resource Manager） | 読み書き | 分単位/プロジェクト（低い） | リクエストパスでの呼び出し |
| Vertex AI / Gemini | リクエスト・トークン | 分単位/モデル/リージョン | ユーザー数比例の呼び出し |
| Cloud SQL | 同時接続数 | インスタンスサイズ依存 | プール未使用・都度接続 |

## ラベル判定ガイド

| 状況 | ラベル |
|---|---|
| リクエスト数・データ件数に比例してクォータ消費が増える構造で、上限・バックオフ・キャッシュのいずれもない | **must** |
| バックオフはあるがジッターがない、リトライ上限がない | **imo**（規模次第で must） |
| 現状の負荷では問題ないが、スケール時にリスクとなる構造 | **imo** + 根拠となる負荷条件を明記 |
| クォータの存在自体を知らせる補足情報 | **fyi** |
| 想定負荷・最大件数が差分から読み取れない | **q**（想定スループットを質問する） |

must と判定する際は「どの条件で顕在化するか」（例: 「秒間10リクエストを超えると Secret Manager のクォータに到達する」）を添えると、開発者が優先度を判断できる。

## 修正提案の定型パターン

指摘の際は、以下のいずれかの具体的な解決策を添える:

1. **キャッシュ**: 起動時取得 + メモリキャッシュ（シークレット・設定値・署名鍵）
2. **バッチ化**: バッチAPI・BulkWriter・ロードジョブへの置き換え
3. **同時実行数制御**: `p-limit` 等によるファンアウトの制限
4. **バックオフ**: エクスポネンシャルバックオフ + ジッター + リトライ上限
5. **シャーディング**: 分散カウンタ・ランダムキーによるホットスポット回避
6. **非同期化**: Cloud Tasks / Pub/Sub 経由でレート制御されたキューに逃がす
7. **クォータ引き上げ**: コードで解決できない正当な負荷なら、クォータ引き上げ申請を案内する
