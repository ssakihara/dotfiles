# レビュー観点 詳細チェックリスト

SKILL.md の Step 4 で参照する。各観点の具体的なチェック項目を定義する。

## 1. 設計（Design）

- 変更がシステム全体のアーキテクチャに適合しているか
- コンポーネント間の責務分担が明確か
- 機能がコードベース・ライブラリ・サービスのいずれに属すべきか正しく配置されているか
- 不要な依存関係を導入していないか
- 既存のパターンや規約と一貫しているか

## 2. 複雑性（Complexity）

- コードが将来の読者にとって理解しやすいか
- 1つの関数・クラスが複数の責務を持っていないか
- 不要な汎用化や将来の仕様への過度な対応（YAGNI違反）がないか
- 深いネストや複雑な条件分岐がないか
- 抽象化のレベルが適切か（過剰でも不足でもないか）

## 3. テスト（Tests）

- テストが正確で、意味のある検証を行っているか
- テストケースが変更の意図を反映しているか
- エッジケースがテストされているか
- テスト自体が保守しやすい設計か（脆いテストでないか）
- テストの命名が何を検証しているか明確に示しているか

## 4. 命名（Naming）

- 変数・関数・クラス名が意図を明確に表しているか
- 略語よりも完全な単語を使っているか（`res` → `tokenResponse`）
- 名前から型や動作が推測できるか
- 一貫した命名規則に従っているか
- マジックナンバー・マジック文字列が定数化されているか

## 5. コメント（Comments）

- 「なぜそうしているか（Why）」が非自明な箇所にコメントがあるか
- 「何をしているか（What）」を説明するだけのコメントがないか（コード自体で表現すべき）
- コメントアウトされたコードの残骸がないか
- TODO/FIXME が放置されていないか
- JSDoc が適切な対象（公開API・非自明な関数）に限定されているか

## 6. スタイル（Style）

- プロジェクトのスタイルガイドに従っているか
- 既存コードとの一貫性があるか
- インデント・空白・改行が統一されているか
- import 文の順序や整理が規約に沿っているか

## 7. ドキュメント（Documentation）

- APIの変更に伴い、関連ドキュメントが更新されているか
- README の変更が必要ないか
- 設定ファイルの変更がドキュメントに反映されているか
- 破壊的変更がある場合、マイグレーションガイドがあるか

## 8. パフォーマンス（Performance）

- N+1クエリ・ループ内クエリがないか
- 不要な `SELECT *` を使っていないか
- WHERE / JOIN / ORDER BY にインデックスが効いているか
- バルク処理すべき箇所で逐次処理していないか
- キャッシュの有無・TTL/無効化戦略が妥当か
- 並列化可能な await を直列実行していないか（`Promise.all` 漏れ）
- 大容量データをオンメモリに展開していないか（ストリーム処理すべき）
- 外部APIコールにタイムアウトが設定されているか

## 9. 負荷耐性（Load Resilience）

- 外部サービス呼び出しにレート制限・サーキットブレーカーが設定されているか
- 障害時のリトライにエクスポネンシャルバックオフ + ジッターが適用されているか（リトライストーム防止）
- キャッシュの一斉失効によるサンダリングハード（thundering herd）を防ぐ仕組みがあるか
- コネクションプールのサイズと枯渇時の挙動が考慮されているか
- キューやバッファにバックプレッシャー制御があるか（無制限にメモリを消費しないか）
- 高負荷時のグレースフルデグラデーション（段階的な機能縮退）が設計されているか
- リソース上限（ファイルディスクリプタ、スレッド数、メモリ）を超えた場合の挙動が安全か
- 長時間実行される処理にキャンセル機構があるか
- クラウドAPIのクォータ（多くはプロジェクト単位・分単位）を高負荷時・スケールアウト時に超過しない構造か
- リクエスト数・データ件数に比例してクラウドAPI呼び出しが増える箇所に、キャッシュ・バッチ化・同時実行数制御があるか
- 429 / `RESOURCE_EXHAUSTED` の応答を正常系の一部として扱うハンドリングがあるか
- **Google Cloud を利用する差分では `references/gcp-rate-limits.md` の詳細チェックを必ず適用する**
