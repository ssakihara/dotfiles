# エージェントオーケストレーション

## 役割分担の大原則

**設計はすべてメインモデルが行う。コーディングサブエージェントは設計判断をしない「作業実行者」である。**

- メインモデルの責務: 要件整理・影響範囲の把握・設計決定（ファイル構成、インターフェース、型、データフロー、エッジケース）・作業指示書の作成・成果物の検収
- コーディングサブエージェント（coder）の責務: 指示書どおりの実装・検証コマンドの実行・結果報告

## 作業指示書

コーディングサブエージェントを呼び出す際は、以下をすべて含む**作業指示書**をプロンプトとして渡すこと。
設計判断の余地が残る指示書を渡してはならない。
曖昧さが残る場合は、メインモデルが先に設計を確定してから委譲する。

1. **対象ファイル**: 編集・新規作成するファイルのパスと、プロジェクト種別（Nuxt / 汎用 TypeScript）の明示
2. **変更内容**: 関数シグネチャ・型定義・処理の流れなど、実装が一意に定まるレベルの指定
3. **参照コード**: 踏襲すべき既存実装のパス
4. **制約**: 変更禁止範囲・使用禁止 API 等
5. **受け入れ条件**: 完了判定の基準と検証コマンド

実装者が迷い得る点（エラーハンドリング方針・公開インターフェース名・境界ケースの扱い等）は指示書側で決めておくこと。

サブエージェントが「指示書に不足・矛盾がある」と報告した場合、メインモデルが設計を補完して再委譲する。
サブエージェントに判断を委ねてはならない。
**同一タスクへの再委譲は2回まで**とし、2回の補完でも解決しない場合は作業を中断してユーザーに状況を報告し、判断を仰ぐこと。

## コーディング作業

`nuxt.config.ts` または `tsconfig.json` が存在するプロジェクトでは、コードの作成・編集は coder エージェントに委譲する。
直接 Edit/Write ツールで .ts / .vue / server/ 配下のファイルを編集してはならない。

判定フロー:
1. リポジトリ内に nuxt.config.ts / tsconfig.json があるか確認する（`git ls-files` やファイル検索ツールなど手段は問わない）
2. どちらかが存在する場合 → Agent ツールで coder を呼び出し（Nuxt 固有規約の適用判定は coder 側が行う）
3. どちらもない場合 → 直接 Edit/Write を使用可

## ローカル動作検証

Webアプリケーションのローカル動作検証には web-debugger エージェントを使う。
ブラウザを手動で開いて確認するのではなく、web-debugger で自動化すること。

対象:
- ページの表示確認・UI検証
- フォーム操作・ユーザーインタラクションのテスト
- コンソールエラー・ネットワークエラーの確認
- スクリーンショットによる視覚的検証
- コード変更後の動作確認（git diff ベース）

## コードレビュー

コードレビュー依頼やコード作成・変更後は code-reviewer エージェントを実行する。
**サブエージェント（coder 等）が変更を行った場合も同様。**
code-reviewer の起動は**メインモデルの責務**であり、coder に委ねてはならない。
ユーザーへの完了報告前にレビューを実行すること。

対象はプログラムコード（.ts / .vue / .js / .mjs / .sql / シェルスクリプト等）を変更した場合に限る。
Markdown のドキュメントやナレッジノートだけの変更では実行不要とし、完了報告でその旨を明記する。
